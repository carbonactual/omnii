# OMNII Product Branch Reconciliation

Status: canonical technical contract beneath the Product Blueprint.

## Branch rule

A product is a composition of canonical objects, shared capabilities, domain capabilities, workflows, integrations, intelligence and human/physical execution. It is not a competing foundation.

## Classification

```text
shared/reusable -> Common Layer
provider-specific -> Adapter
product-specific -> Branch
historical -> Lineage only
unknown -> Provisional / investigate
```

## Branch integration contract

Every branch MUST identify:

```text
canonical objects reused
shared capabilities reused
domain capabilities added
identity/authority model
data boundaries
integrations
workflows
human execution
physical execution
Pulse/Value outputs
security/continuity behavior
reusable improvements returned to common fabric
```

## Extraction rule

When functionality is needed across two or more branches, evaluate promotion into the shared capability fabric. Do not copy the implementation into each product unless the behavior is genuinely domain-specific or isolation is required.

## Boundary examples

- Charter fleet is a movement-asset composition, not a new universal fleet primitive.
- Bunk property records use the universal object and relationship model.
- NGIN institutional workflows use common identity, authority, registry, evidence and governance capabilities.
- RITES continuity workflows use canonical identity, relationship, documents, resources and lifecycle capabilities.
- NAIRE financial workflows inherit the economic ontology and logical ledgers.

## Contribution loop

```text
branch execution -> Pulse/evidence -> evaluation -> generic improvement -> shared fabric
```

A product that improves the ecosystem should leave a reusable capability, adapter, evidence pattern, knowledge artifact or validated integration where appropriate.
