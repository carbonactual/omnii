# Carbon Actual Product Blueprint v1.0

**Status:** FROZEN — composition architecture
**Ecosystem:** Carbon Actual
**Effective date:** 2026-08-18

## 1. Product Doctrine

A Carbon Actual product is not a standalone invention. It is a composition of shared capabilities, domain configuration, workflows, intelligence, integrations, data contracts and physical/human execution.

> **Need → capabilities → composition → deployment → Pulse → Value → curation → optimization → next version.**

The architecture is intentionally LEGO-like: reusable pieces are built once, versioned, improved and recomposed across domains.

## 2. Universal Product Shape

Every product blueprint SHOULD contain:

```text

```

## 3. Product Assembly Workflow

### Step 1 — Intake

Capture the request in plain language and identify the requesting human, organization, government, association or other entity.

### Step 2 — Discover

ABBA/curation identifies needs, constraints, entities, capabilities, dependencies and opportunities.

### Step 3 — Compose

Select existing shared capabilities before creating new ones.

### Step 4 — Integrate

Connect external open source, open alternative, white-label, SDK, AI, agent, ledger, blockchain, hardware or institutional systems through adapters.

### Step 5 — Configure

Apply domain rules, roles, workflows, policies, data boundaries, branding and local requirements.

### Step 6 — Validate

Run security, privacy, authority, data, economic and workflow checks.

### Step 7 — Deploy

Deploy the digital and physical/human components required for the use case.

### Step 8 — Measure

Capture Pulse and Value.

### Step 9 — Curate

ABBA identifies failures, opportunities, unused capacity, capability gaps and next actions.

### Step 10 — Improve

Promote generally reusable improvements back into the shared capability fabric.

Capital experimentation/deployment surface composed from opportunities, due diligence, ownership, investment, financing, contracts, risk and reporting.

## 7. Physical + Digital + Human-Ware Rule

Every product blueprint must ask whether the requirement includes:

- software
- hardware
- human execution
- AI execution
- agent execution
- facilities
- machines
- physical logistics
- maintenance
- emergency response
- training
- social interaction

A product is incomplete if its real-world outcome depends on a physical/human component that the blueprint ignores.

 ↓

 ↓

The user should feel that the ecosystem understands context and curates the next useful step rather than presenting an undifferentiated list of features.

## 11. Reuse Rule

If a capability is needed by two or more products, evaluate promotion into the shared fabric.

If an improvement is generic, improve the shared capability rather than patching each product separately.

If a feature is domain-specific, keep it inside the branch.

If a branch creates a new shared primitive, submit an architecture amendment rather than silently creating a new constitutional layer.

## 12. Product Quality Gate

A product is ready for release only when its blueprint can answer:

1. Who/what is the entity?
2. What authority exists?
3. What capability is being provided?
4. What human work is required?
5. What intelligence work is required?
6. What physical work is required?
7. What data is collected and why?
8. What integrations are used?
9. What happens when an integration fails?
10. How is Pulse measured?
11. How is Value measured?
12. What is the Value Baseline?
13. What is monetized?
14. What is protected?
15. What becomes Ash?
16. How is recovery handled?
17. How does the product contribute reusable capability back to Carbon Actual?
18. How does the user continue/exit/migrate?

## 13. Freeze Rule

No new Carbon Actual product should introduce a new top-level architecture merely because it is a new market.

The default action is:

> **Discover → compose → integrate → configure → deploy → measure → curate → improve.**

That is the product factory.
