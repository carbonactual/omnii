# Carbon Actual Kernel Build Order

**Status:** Canonical implementation sequence

This document turns the architecture into an implementation sequence without prematurely locking vendors or product-specific technology.

## Phase 0 — Constitutional invariants

Freeze:

- identity and authority separation
- provenance requirements
- capability contracts
- privacy/security baseline
- lifecycle semantics
- composition rules
- integration replaceability
- human agency principles
- unknown-state preservation

## Phase 1 — Universal object kernel

Implement the canonical object envelope, identifiers, versions, lifecycle, provenance, authority references, relationships, permissions and extension mechanism.

**Output:** every future Carbon Actual object has a common addressable shape.

## Phase 2 — Registry kernel

Implement registry interfaces and indexes for Entity, HASH, Authority, Intelligence, Capability, Swarm, Team, Relationship, Provenance, Event/Pulse, Value, Contract, Resource and Integration.

**Output:** the ecosystem can discover and connect its objects.

## Phase 3 — Capability/Swarms/Teams kernel

Implement capability contracts, Swarm membership/evaluation and dynamic Team composition.

**Output:** the ecosystem can assemble capability instead of hard-coding products.

## Phase 4 — Workflow/orchestration kernel

Implement reusable workflow primitives, human-in-the-loop steps, agent steps, automated steps, physical execution, approvals, retries, exceptions, compensation and audit.

ABBA can orchestrate within declared authority and policy boundaries.

## Phase 5 — Identity/authority kernel

Implement HASH, SEAL, delegation, consent, selective disclosure, revocation and continuity.

Human authority must remain explicit.

## Phase 6 — Event/Pulse/Value kernel

Implement event capture, evidence, Pulse normalization and multidimensional Value measurement.

Do not freeze the final economic formula until validated with real datasets and scenarios.

## Phase 7 — Economic/ledger kernel

Implement asset/liability classification, rights, contracts, logical ledgers, settlement interfaces and tokenization adapters.

Blockchain is one possible implementation family.

## Phase 8 — Integration kernel

Implement adapter contracts for APIs, SDKs, MCP, agent protocols, identity systems, databases, ledgers, blockchains, hardware and physical providers.

Every provider must be replaceable behind a capability contract.

## Phase 9 — Security/Ash/Phoenix kernel

Implement policy evaluation, least privilege, isolation, provenance, anomaly handling, quarantine, recovery, Ash classification and Phoenix response workflows.

No unrestricted destructive autonomy.

## Phase 10 — Product Composer

Implement the request-to-product pipeline:

`request → outcome → capabilities → Swarms → Team → workflow → integrations → governance → deployment → Pulse → Value → learning`

## Phase 11 — First reference branches

Use existing Carbon Actual products as reference compositions rather than separate architectures:

Institute GPT, Noun Student Bot, NGIN/RITES, Bunk, Charter, Logistico, Sportist, TIP, Build Labs, Spare, HAPI, HAPI World, HAPI Bank, NAIRE, Marketplace and Capital Block.

The purpose is to prove that common denominators genuinely compose across domains.

## Phase 12 — Physical-world expansion

Connect the same capability contracts to human operators, vehicles, buildings, machines, IoT, robotics, logistics, maintenance and other physical execution.

## Phase 13 — Continuous Becoming

Use Pulse, Value, capability evidence, relationships and opportunity data to continuously curate next actions while preserving consent and human agency.

## Completion criterion

The kernel is ready when a new product can be specified primarily as a composition of existing canonical objects/capabilities and only introduces new primitives when the architecture demonstrably lacks one.
