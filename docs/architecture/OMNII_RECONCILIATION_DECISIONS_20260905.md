# OMNII Reconciliation Decisions — 2026-09-05

This record captures material contradictions or duplicated semantics found during the second estate sweep. The selected formulation is the one that best preserves constitutional boundaries, human/legal authority, reuse and interoperability.

## R1 — HAPI World role

**Sources:** `carbonactual/hapi-world/CONSTITUTION.md`, `carbonactual/hapi-world/CANON.md`, ABBA HAPI World material, current OMNII foundation.

**Conflict:** An earlier HAPI World draft describes HAPI World as a sovereign AI civilization with autonomous constitutional authority and a 13-layer architecture. The same repository explicitly marks that draft as superseded by `CANON.md`; the current OMNII architecture additionally separates constitutional substrate from operating environments/common capabilities.

**Decision:** HAPI World is a shared human/AI participation environment/common denominator built on OMNII. It may host persistent AI-world capabilities, but it does not create an alternative constitutional authority layer. Its governance, identity, memory, resource, knowledge and movement capabilities consume OMNII constitutional/runtime contracts.

**Reason:** This preserves the strongest world/continuity concepts while preventing a second constitution above or beside OMNII.

## R2 — Human authority vs AI governance

**Sources:** HAPI World CANON, ABBA/ABBA MAS governance material, OMNII authority model.

**Conflict:** Some legacy text makes Carbon Actual itself the absolute constitutional authority and assigns autonomous AI councils roles resembling sovereign governance. OMNII now defines human/legal authority and SEAL as controlling boundaries for consequential actions.

**Decision:** AI councils, ABBA, agents and automated authorities are institutional/runtime participants whose legitimate powers derive from valid governance/human/legal authority. They cannot elevate their own authority, amend the constitution, or override human/legal authority.

## R3 — Identity/# and HAPI

**Sources:** HAPI World CANON, HAPI AI foundation docs, RITES, OMNI, BUNK.

**Conflict:** Several products historically represent the human identity, # identity and product account differently.

**Decision:** One shared identity semantics is canonical. Product accounts, institutional identifiers and provider identifiers are projections/credentials/relationships. HAPI participation must link to the shared identity route rather than mint duplicate human identity semantics.

## R4 — Memory

**Sources:** Continuum memory, HAPI World Memory Anchor, OMNI memory, SPARE ownership memory, ABBA MAS swarm memory.

**Decision:** Memory is a reusable knowledge/continuity capability with explicit subject, scope, consent/authority, provenance, confidence, retention and lifecycle. Providers are storage/adaptor choices, not canonical semantics.

## R5 — Product registries

**Sources:** Carbon Actual product registry v2, ABBA command-center product registry, OMNI ecosystem registry, OMNII product registry, NASC master export.

**Decision:** OMNII product estate is canonical. Legacy registries become source projections/imports. Product status remains evidence-based. Historical/legacy names are not silently promoted to built products.

## R6 — Token/currency/value

**Sources:** ABBA MAS Base Value Token laws, IO/token ledger foundation, existing OMNII economic ontology/runtime.

**Conflict:** Some source text calls Base Value Token the ecosystem currency, while other formulations separate value, token representation, ownership/rights and settlement.

**Decision:** Value/PULSE are canonical economic semantics; tokenization is a representation/transformation step. A token may represent eligible value/rights but is not by itself proof of legal ownership, authority, or settlement. External accounting and law remain controlling.

## R7 — Registry as capability

**Sources:** intelligence exchange registry, ENS registry, ecosystem registry, product registry, NASC registry, integration registry, GitHub asset registry, ECC registry.

**Decision:** Registry is a reusable capability with typed domain instances. It is not a separate constitutional layer. Each registry record retains owner, scope, provenance, lifecycle and source lineage.

## R8 — Workflow/automation

**Sources:** NASC, ABBA automation, workflow, Thunderbolt, Zapier integration configs.

**Decision:** Form → intent → workflow → task → execution → evidence → outcome is one reusable workflow fabric. Automation/provider implementations are replaceable adapters. Human/authority gates remain outside provider automations.

## R9 — Agent authority

**Sources:** RITES Agent Registry, ABBA agent spec, ABBA MAS, OMNII agent constitution/runtime.

**Decision:** Agents are bounded operators. Registration, planning, delegation, coordination and evaluation are reusable capabilities. Authority must be explicit, scoped, revocable and traceable. Consensus, capability or intelligence cannot manufacture authority.

## R10 — Atlas vs operational truth

**Sources:** Audubon/Atlas doctrine, Cultural Atlas, HAPI Nexus, OMNI presentation layers.

**Decision:** Atlas is governed representation/discovery/curation. Operational truth remains in canonical OMNII state/evidence. Atlas may be stale, filtered or audience-specific and must carry provenance/context.

## R11 — ECC/provider frameworks

**Sources:** ECC, OpenClaw, CrewAI, PraisonAI, Botpress, Baserow, MCP, model providers.

**Decision:** Absorb useful patterns behind provider-independent contracts. Do not make any provider/framework a constitutional dependency. ECC is explicitly not required for canonical OMNII operation.

## R12 — Audubon design

**Sources:** Audubon Continuum doctrine and Ecological Build Method.

**Decision:** Audubon is a reusable ecological/design intelligence method: being + habitat + relationship + Plate/Book composition. It is not a fixed visual skin and does not modify constitutional semantics.
