# Carbon Actual Universal Capability Architecture

**Status:** Canonical architecture contract

## Foundational correction

Carbon Actual must not be divided into separate foundational worlds called **physical** and **digital**.

That distinction is an implementation detail, not an ontological boundary.

A capability may be implemented by one or more of:

- a human
- an intelligence
- software
- hardware
- an organization
- a machine
- an environment
- a resource
- a combination of any of these
- future classes not yet known

The ecosystem models the capability and its participants first, then records how that capability is implemented.

## Universal composition

```text
INTENT / NEED
     ↓
OUTCOME
     ↓
CAPABILITY
     ↓
IMPLEMENTATION(S)
     ↓
HUMAN / INTELLIGENCE / SOFTWARE / HARDWARE / ORGANIZATION / RESOURCE
     ↓
TEAM + WORKFLOW
     ↓
ACTION
     ↓
EVENT / PULSE
     ↓
VALUE / RESPONSIBILITY
     ↓
LEARNING / BECOMING
```

No implementation category is constitutionally privileged.

## Participant model

A participant can possess multiple roles simultaneously.

For example, a human can be:

- identity subject
- authority holder
- capability provider
- resource owner
- learner
- customer
- team member
- steward
- beneficiary

An intelligence can similarly be:

- capability provider
- team member
- orchestrator
- learner
- economic participant where authorized
- tool user
- delegated actor

A machine can be a resource, capability provider, sensor, actuator, team member or autonomous service subject to applicable authority and safety rules.

## Implementation model

Implementation is represented separately from capability.

```text
CAPABILITY
   │
   ├── human implementation
   ├── intelligence implementation
   ├── software implementation
   ├── hardware implementation
   ├── organizational implementation
   └── composed implementation
```

This allows Carbon Actual to replace or combine implementations without changing the underlying capability contract.

## State is contextual

The ecosystem is not stateless and is not permanently fixed.

Its state is continuously derived from:

- active entities
- relationships
- events
- Pulse
- Value
- obligations
- resources
- capabilities
- availability
- context
- governance
- risk
- time
- environment
- current objectives

Therefore the ecosystem is **formless in composition but governed in principle**.

## No permanent product boundaries

A product is a Product Branch, not a sealed universe.

A branch may consume capabilities from another branch and expose capabilities to other branches.

Examples:

- Institute GPT can provide education capabilities to government, organizations and individuals.
- Spare can provide maintenance/replacement capabilities to Charter, Bunk, Build Labs or any future branch.
- HAPI can provide human capability to any authorized Team.
- HAPI World can provide intelligence capabilities to any authorized Team.
- Capital Block and Nano Banking capabilities can support branches without becoming their identity layer.

## Human + AI principle

Human and intelligence are complementary participants.

The HASH can associate a human with a dedicated intelligence environment, but neither identity nor authority is silently transferred between them.

The objective is augmentation, coordination, balance, capability and continuity—not replacement of human agency.

## Hardware + software principle

Hardware and software are implementation substrates.

A smart vehicle is therefore modeled as a composition of capabilities, resources, sensors, actuators, intelligence, software, hardware, identity, authority, maintenance, energy and relationships rather than as a separate "physical product" architecture.

The same rule applies to buildings, robots, machines, infrastructure, devices, tools and future systems.

## Unknown/future principle

Carbon Actual must not require advance enumeration of every possible participant.

A new participant class can enter through the universal Entity and Capability contracts while preserving:

- identity
- authority
- provenance
- Providence
- safety
- governance
- privacy
- value/accountability
- lifecycle

This supports future biological, artificial, autonomous, collective, extraterrestrial or otherwise novel participants without changing the core model.

## Universal LEGO rule

A new product should require only:

1. a mission/outcome,
2. canonical objects,
3. existing capabilities where available,
4. selected Swarms,
5. a Team,
6. workflows,
7. integrations,
8. domain-specific extensions only where necessary.

If a proposed product repeatedly requires the same new primitive, that primitive should be promoted into the universal kernel rather than copied across products.

## Architectural compression rule

Do not create separate foundations for:

- human vs AI
- physical vs digital
- hardware vs software
- online vs offline
- product vs service
- internal vs external provider

Where the difference is operationally important, model it as a **role, implementation, context, interface, policy or capability subtype**.

This keeps the ecosystem small, composable and extensible while retaining the distinctions required for safety, governance and execution.
