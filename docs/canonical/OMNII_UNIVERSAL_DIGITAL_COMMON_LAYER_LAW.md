# OMNII Universal Digital Common Layer Law

**Status:** Canonical constitutional extension  
**Parent:** `CANON.md`  
**Scope:** Every canonical object, product, provider adapter, agent, service, institution, external integration, and consequential workflow

## 1. Purpose

The Universal Digital Common Layer is the shared semantic and governance substrate that lets the ecosystem integrate with the ordinary internet without inheriting the internet's fragmented account/application/provider boundaries as constitutional truth.

It does not replace existing protocols. It maps them into a stronger canonical model.

## 2. Canonical Dimensions

Every material ecosystem object or workflow should be expressible through:

`entity, identity, authority, relationship, capability, intent, policy, state, event, evidence, provenance, dependency, continuity, portability, trust, settlement, liability, lifecycle`

A domain, repository, bank account, organization, agent, service, physical asset, media item, credential or event may use different subsets, but shared semantics must remain interoperable.

## 3. Core Separations

- Identity != authority.
- Authentication != authorization.
- Ownership != account access.
- Capability != permission.
- Intent != implementation command.
- Representation != underlying canonical object.
- State != configuration snapshot.
- Settlement != liability.
- Provider relationship != constitutional dependence.
- Recovery != privilege escalation.

## 4. Universal Object Contract

Canonical objects must have a stable identifier, type, version, state/status, identity, authority, provenance, relationships, dependencies, capabilities, timestamps and extensible attributes, with explicit support for intent, policy, trust, evidence, events, continuity, portability, settlement, liability and lifecycle where applicable.

## 5. Authority and Delegation

Every consequential action must resolve:

`principal → authority grant → capability → action`

A delegation carries principal, delegate, scope, resource, operation, conditions, limits, duration and revocation state as applicable. Multi-hop delegation preserves the complete chain.

## 6. State and Events

Material state changes are events. Events carry actor, authority context, action, object/subject, time/context, previous state, new state, provenance, result and evidence references as applicable.

Unknown or provider-specific state must be preserved until classified rather than discarded or coerced into a false known state.

## 7. Evidence and Provenance

Every material claim must be classifiable by provenance and supported by evidence at the required assurance level. Transformation, migration and composition preserve lineage or explicitly mark an unavailable boundary.

## 8. Dependency and Continuity

Canonical services are modeled as dependency graphs where relevant. Critical dependencies must identify ownership/controller, capability, criticality, provider, replacement options, failure behavior, last-known-good state and continuity path.

Provider failure must not erase canonical state.

## 9. Portability and Exit

Portability includes semantics, relationships, permissions, authority context, configuration, provenance, lifecycle state, evidence, dependencies and handoff metadata when those elements are material to continued use.

A provider adapter must not make exit impossible by hiding canonical meaning in proprietary state.

## 10. Trust

Trust assertions carry source/issuer, scope, evidence, time, status, confidence and revocation/replacement information as applicable. Trust may be delegated but does not create authority by itself.

## 11. AI and Agents

AI entities and agents participate as canonical actors. They may only perform consequential actions under explicit authority. Each action preserves principal, delegation, capability, intent/context where known, tool/provider path, result, evidence and liability context.

## 12. External Internet Integration

The ecosystem may integrate with DNS, DNSSEC, TLS/PKI, WebAuthn, OAuth, DIDs, Verifiable Credentials, ENS/HNS and other naming/credential systems, APIs, MCP, A2A, cloud platforms, repositories, registries, payment networks, messaging systems and physical infrastructure.

These are transport, trust, naming, execution or provider mechanisms. They do not supersede canonical ecosystem semantics.

## 13. Loophole Tests

Any proposed integration fails conformance if it can:

1. convert authentication into unbounded authority;
2. erase the principal through delegation;
3. lose canonical state during provider exit;
4. conceal a material state transition as an ordinary configuration change;
5. sever provenance without declaring the evidence boundary;
6. create a duplicate truth under a product-specific identifier;
7. execute through a lower-level interface after a higher-level gate denied execution;
8. give an agent broader authority than the delegating principal granted;
9. make material events non-reconstructable without lawful reason;
10. hide dependencies whose failure materially affects continuity.

## 14. Product Rule

Products compose the common layer. They may specialize or configure it for domain purposes. They may not create a competing universal object model, identity system, authority kernel, event truth, dependency graph or portability semantics.
